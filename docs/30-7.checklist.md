## 6. Backend Architecture Upgrades

No major architecture rewrite is currently required. Keep the modular monolith and four-process runtime, and strengthen its existing reliability guarantees.

### Near-Term Architecture Improvements

- [ ] Add reconciliation tooling that compares Redis auction authority with the PostgreSQL projection.
- [ ] Make reconciliation report differences in sequence, version, price, leader, winner, deadline, and order state.
- [ ] Require maintenance mode and explicit verification before any automated repair changes authoritative state.
- [ ] Add failure-recovery tests for crashes between:
  - [ ] Redis mutation and Stream append.
  - [ ] PostgreSQL projection commit and Redis Stream acknowledgement.
  - [ ] Outbox publication and `delivered_at` persistence.
  - [ ] Kafka processing and offset commit.
  - [ ] Email provider acceptance and delivery-state persistence.
- [ ] Verify stable idempotency keys for bids, buy-now, checkout, Kafka consumers, email delivery, and admin retry operations.
- [ ] Add outbox retention or archival rules for delivered events.
- [ ] Monitor the oldest pending outbox event, retry counts, terminal events, and poison-event handling.
- [ ] Formalize order and payment behavior as explicit state machines.
- [ ] Enforce state transitions transactionally and validate the actor's role for every transition.
- [ ] Standardize validation, response envelopes, error codes, pagination, and request IDs across APIs.
- [ ] Expand refresh-token rotation, token-reuse detection, CSRF, rate-limit, audit-log, and secret-redaction tests.
- [ ] Remove deprecated workers and superseded architectural paths after verifying that no runtime or script depends on them.

### Conditional Scaling Work

The current single sequential `auction-worker` preserves global Stream ordering. Do not redesign it without evidence that projection lag is a real bottleneck.

- [ ] Measure projector throughput, Redis Stream lag, pending entries, reclaim frequency, and projection convergence under realistic load.
- [ ] Document the one-replica `auction-worker` constraint and its correctness rationale.
- [ ] Add warning and critical thresholds for Stream lag, pending entries, and stale worker heartbeats.
- [ ] Keep the single-worker design if it satisfies measured throughput and recovery targets.
- [ ] If it becomes a proven bottleneck, partition events by `productId` or auction aggregate.
- [ ] Preserve per-auction ordering while allowing different auctions to be projected concurrently.
- [ ] Prove the partitioned design with concurrency, rebalance, crash-recovery, duplicate-delivery, and ordering tests before enabling multiple worker replicas.

### Optional High-Value Features

Implement these only after the near-term correctness and evidence work is complete.

- [ ] Add a payment lifecycle with pending, paid, failed, expired, cancelled, and refunded states.
- [ ] Handle payment webhooks with signature validation, replay protection, idempotency, and transactional order updates.
- [ ] Add a searchable audit trail for moderation, bidder bans, account changes, order transitions, DLQ retries, and administrative actions.
- [ ] Add an operational reconciliation view for Redis/PostgreSQL agreement, Stream lag, outbox backlog, Kafka lag, and worker health.
- [ ] Add controlled maintenance, Redis rebuild, event replay, and post-recovery verification commands.
- [ ] Add notification preferences, unsubscribe behavior, template versioning, and delivery history.

### Architecture Changes to Avoid for Now

- [ ] Do not split the modular monolith into microservices without a measured organizational or scaling need.
- [ ] Do not add Kubernetes, another message broker, or another cache only for technology breadth.
- [ ] Do not claim exactly-once delivery; document at-least-once delivery with idempotent effects.
- [ ] Do not add a PostgreSQL bidding fallback when Redis is unavailable, because that would create split authority.

## Techniques to Prioritize

- End-to-end browser testing.
- Failure-injection and recovery testing.
- Structured logging, metrics, and distributed tracing.
- Accessibility testing.
- Route-based code splitting.
- Evidence-backed database and performance optimization.

Avoid adding more infrastructure technologies for now. The project will gain more CV value by making its existing correctness, resilience, performance, and architecture easy to verify.
